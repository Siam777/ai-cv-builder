# Q4 criterion coaching: local provider integration

Status: 2026-10-11. The prepared contract/review UI now connects to the configured OpenAI provider after the user's explicit go-ahead for the described payload/destination. In-app consent remains required. No live provider request or model-quality evaluation is claimed. PLAN.md owns progress. Release scope and distributed skills are unchanged.

## Prepared behavior

Each current job criterion offers a focused coaching panel. Availability follows the server-only OpenAI configuration. Without a key, valid coaching requests return `AI_NOT_CONFIGURED` after ownership/revision/context checks and before reserving usage. Configured requests use the existing account request ledger and proposal decision service. The general bullet assistant retains its behavior and existing request hashes so pending pre-integration rewrites remain retryable.

The staged request includes an owned CV ID/revision, selected bullet, writing instruction, consent and bounded posting review inputs. The posting goes to the app server for deterministic validation. The prepared context resolver rebuilds criterion IDs/source spans and checks posting/CV hashes and rule versions. It excludes hidden sections and unsupported languages, enforces the existing 10-bullet/12,000-character entry bound, preserves reviewed priority origin and returns only the selected criterion and target context. No contact object, other entry or full posting enters the proposed provider context.

The local reply validator accepts a structured assessment (`relevant`, `uncertain`, `not_demonstrated`), explanation, candidate citations, questions and optional selected-bullet rewrite. `relevant` is shown as **Possible relevance — inspect the evidence**, not a verified qualification. Candidate citations resolve to current bullets within the selected entry. Job requirements and target seniority are desired context, not candidate facts. Local coverage counts stay unchanged.

The integration requires independent assessment and rewrite support verdicts obtained by the server. The rewrite check uses candidate evidence only. Without these verdicts, or with failed checks, unsupported numbers, non-English context or a duration requirement, the validator returns a withheld edit and a clarification question. Uncertain/absent support cannot generate an applicable edit. These checks are defenses, not guarantees of entailment; model/independent reviewer errors remain possible.

The UI previews the exact criterion, context and entry bullets before consent. It shows assessment citations, before/after wording and rewrite references. Acceptance requires explicit factual confirmation; rejection preserves the CV. Prepared proposals use the existing server-owned proposal schema, account decision transaction, revision/idempotency checks and session Undo. Source changes disable client acceptance and are rejected server-side. Changing criterion/priority resets coaching. Account-data export already includes stored proposal metadata; no migration or alternate persistence path is introduced.

## Authorized provider integration

During preparation, automatic approval review rejected adding OpenAI job-coaching requests without explicit approval for the sensitive candidate/job payload and destination. The user subsequently said "ok go ahead for next" after the progress report identified that payload and destination. This authorized implementing the reviewed integration. In-app consent is still mandatory before a product user requests generation. No live provider call was made during implementation or verification.

Implemented calls to **OpenAI** contain **the selected entry's bullets, one selected job criterion, target role/seniority/language/company and the writing instruction**, only after explicit in-app consent. The app server receives the full posting solely to validate the selected criterion; the provider receives the selected criterion, not the full posting or CV contact fields. Entry text itself may include candidate-entered personal information, which is included in the consent preview. The preview now includes the target company as well as role, seniority and language.

The existing request ledger reserves one application attempt using shared daily/concurrency limits. Coaching hashes include all bounded job-review inputs; changed instruction, target, priority or action conflicts on retry. Valid identical retries return the immutable stored proposal without another provider call or quota charge. Failed generation stays failed rather than automatically paying for another attempt. The configured model uses versioned prompts, strict structured replies, one shared 45-second deadline and no paid retries. Up to three calls: coaching draft, assessment/message/questions audit, and candidate-only rewrite audit. The rewrite auditor receives only original cited evidence and proposed text, excluding criterion, target and instruction. Citations are validated before audits; uncertain/absent support, invented metrics, failed checks and duration requirements cannot produce edits. Provider failures at any stage return an error without changing the CV. Requests specify `store: false`; provider retention depends on deployment/account settings. Selected-criterion metadata and entry references use the existing proposal record and account export, with no migration.

Official API shape checked against [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs) and [Responses migration/storage guidance](https://developers.openai.com/api/docs/guides/migrate-to-responses). These sources establish request formatting and storage controls, not factual accuracy or zero retention.

## Validation and remaining gates

Five coaching unit scenarios cover request/context bounds, source hashes/versions, priority origin, hidden evidence, citations, independent-verdict withholding, original/source preservation, stale revision/undo, unconfigured ownership/zero-usage, configured adapter payloads and real ledger/decision behavior. The adapter asserts exclusion of private contact fields, other-entry text and a full-posting sentinel; its rewrite auditor receives only original cited sources and proposed text. Controlled failures at each of the three call stages cover timeout, HTTP failure, malformed/incomplete/refused and oversized replies, with no automatic retry. Account persistence checks consent, unchanged CV, immutable retries and changed-context conflicts, shared daily/global/concurrency limits, failures, stale generation, accept/reject and deletion. A legacy hash assertion protects pre-existing general rewrite retries. A versioned twelve-case **development** fixture covers supported research wording, related clouds, assistance/leadership, learning, negation, compound gaps, duration, new metrics, in-progress credentials, uncertainty, entry-specific absence and supported outcomes. Verdicts and replies are controlled; these cases do not evaluate a live model.

Six coaching browser scenarios use synthetic verified accounts. The normal configuration checks the real unavailable service and three browser-injected proposal flows using real SQLite decisions, confirmation/rejection, export, idempotency, Undo, lost-response recovery and source conflicts. Two opt-in configured cases use the actual server adapter and ledger with a test-only synthetic OpenAI transport: one exercises lost-response recovery, single quota/record, save-once/export and Undo; the other exercises failed independent assessment with no applicable edit or CV change. All OpenAI traffic is intercepted locally. The preload refuses production, non-test databases and real credentials and is loaded only by the isolated test runner. Mobile wrapping is checked and captured in `test-results/job-coaching/mobile-controlled-review.png`.

Current verification: all 117 unit tests, typecheck and isolated production build passed. The affected browser run passed 21 cases (2.4 minutes) with two opt-in configuration skips, then both configured synthetic-provider cases passed (18.6 seconds): all 23 distinct affected scenarios passed across the two runs. Final six focused unit checks passed after adding full-posting sentinel, concurrency and legacy-hash assertions. The full browser suite was not repeated.
