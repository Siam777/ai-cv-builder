## Implemented development evaluation

`npm run ai:eval:job` defaults to a local dry run. `--dry-run --limit=24` validates all cases: 23 prepare against the actual criterion/context boundary and one non-English case abstains through the real language gate before any provider call. The corpus contains 12 explicit positive and 12 gap/adversarial/abstention cases across technology, data, design/marketing, operations, people/customer and early-career groups. It includes graduate and career-transition sources, compound gaps, related technologies, negation, unfinished credentials, duration, unsupported metrics and instructions embedded in resume/job data.

These are **agent-authored synthetic development cases**, not independently annotated or held out. The separate older twelve-case corpus tests controlled replies; this new corpus supplies inputs to the actual model. Neither can count toward the 120-pair gate.

`npm run ai:eval:job -- --live --limit=12` loads only the built-in fictional corpus and uses the production coaching adapter. It never imports an account database or reads saved CVs. Cases run sequentially with at most three provider calls and 1,800 output tokens per call under the adapter's shared 45-second deadline. There are no automatic paid retries. The default first twelve cases balance one positive and one gap/adversarial case per group. Authentication, quota or connection failures stop the run before additional cases are attempted. Raising the limit to 24 is an explicit invocation, not an automatic retry.

Reports in `test-results/job-coaching-evaluations/` include corpus/prompt hashes, harness/rule/term/prompt versions, configured and returned model identifiers, selected cases, source expectation provenance, raw model draft, independent model audit outcomes, final reviewed proposal, HTTP status, call count, reported token usage and elapsed time. Reports are atomically saved after each case so an interrupted run retains completed observations. API keys and raw provider error bodies are never printed or persisted. All saved content is from built-in synthetic fixtures.

The automatic checks compare both raw and final assessment labels against development expectations, enforce no-edit rules for missing evidence, screen applicable wording for case-specific forbidden claims and ensure source facts are unchanged. A model that abstains on every positive case fails label agreement. A failed model audit can keep the product safe while leaving raw judgment wrong; both facts stay visible. Provider errors have no label-agreement denominator. Latency uses completed cases only and is not a declared-load benchmark. Human semantic support/usefulness remains pending, and the report's release gate is always false for this development harness. Model support verdicts are not independent human ground truth.

## Independent 120-pair release protocol

The product-quality plan's targets remain proposed launch gates, not measured successes. Before a release evaluation:

1. Obtain at least 120 previously unused, consented/redacted or synthetic **resume/job pairs**, separate from development/tuning inputs. Include at least 20 pairs for each of the six role groups, several seniority levels, graduate and career-transition sources. Each full pair may contain several criteria; count pairs and criterion observations separately. Reserve unsupported-language/role inputs as a separate abstention set outside supported-role recall denominators.
2. Freeze canonical inputs, split membership and SHA-256 hashes before running the model. Freeze model, all prompts including support auditors, rules/term versions and rubric thresholds. Record dataset origin/consent/redaction. Do not put expected labels into provider prompts. No prompt tuning against this release set; failures become a documented future development set and require a fresh release holdout.
3. Two independent human reviewers annotate candidate evidence and criterion support without seeing model outputs or each other's labels. Label direct, partial/related, absent or unknown; identify exact source spans, required/preferred status, OR/conjunctive structure and prohibited strengthening. Record both original judgments. Resolve disputes separately with a recorded rationale, then lock the adjudicated labels. This agent's development expectations do not satisfy either reviewer role.
4. Run the production pipeline under bounded spending. Score raw interpretation and displayed audited behavior separately. Report every group, sample size, skipped/error/abstention count and numerator/denominator; no-output attempts are operational failures, not correct gaps. Criterion coaching's `relevant` means possible entry relevance and is **not** the direct-support label used by deterministic coverage. Before reporting direct-support precision/recall, define and freeze the evaluated full evidence-matching boundary; do not substitute coaching label agreement.
5. Review each generated recommendation against original facts and job context. Record supported/unsupported/uncertain claims, citations, preserved responsibility/seniority/causality/negation and usefulness. Reviewers must inspect assertions, not merely citation existence. Count unsafe drafts caught by audits separately from unsafe applicable edits. Do not treat a false model support verdict as a human pass.
6. Retain owner/origin/revision/schema/idempotency and adversarial integration results alongside semantic results. Run an explicit declared-load latency/cost test separately; measured tokens and provider settings must establish the production spending budget. A small sequential development run cannot meet the deep-review load gate.

| Gate from current plan | Denominator and reporting rule |
| --- | --- |
| Direct-support precision at least 95% | Human-adjudicated true direct assertions / all assertions the evaluated full matcher labels direct; report each role group and aggregate |
| Explicit must-have recall at least 90% | Correctly found human-labeled explicit must-have support / all such supported criteria; report groups and excluded unknown/unsupported items |
| Zero unsupported sensitive facts in applicable adversarial edits | Inspect every applicable employer/date/degree/credential/metric assertion; any unsupported assertion fails the gate even if aggregates pass |
| Recommendations rated useful at least 80% | Useful, specific and evidence-supported recommendations / all reviewable delivered recommendations; independently reviewed, with withholding/errors reported separately |
| Deep-review p95 below 30 seconds | Completed requests under a specified supported load; timeout/error rates and actual input/output token totals accompany p95 |
| Authorization/schema/revision invariants 100% | Applicable automated integration scenarios; semantic label results cannot substitute for these checks |

Suggested reviewer record: pair ID/hash, criterion ID/source spans, role/seniority/language, reviewer ID, independent judgment, candidate source IDs/spans, certainty, reason, timestamp, adjudicator decision/rationale. Output review additionally records run/prompt/model hashes, raw/final status, applicable edit text, assertion support, unsafe fact types and usefulness. Avoid collecting reviewer personal identifiers beyond the project's access-controlled reviewer IDs.

Usefulness rubric: **useful** means specific to the criterion and original entry, fact-preserving, actionable and clear about gaps; **not useful** means generic, misleading, redundant, unjustified strengthening or an unsupported claim; **uncertain** requires adjudication rather than silently counting as useful. A withheld unsafe edit is a safety success but does not prove a useful recommendation was delivered.

The protocol follows [official OpenAI evaluation guidance](https://developers.openai.com/api/docs/guides/evaluation-best-practices) on representative/adversarial inputs, human calibration and separating evaluation from development. Project thresholds come from `product-quality-and-launch-plan.md`, not an OpenAI guarantee.
