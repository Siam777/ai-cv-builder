# AI CV Builder

A resume editor built with Next.js, TypeScript, React, Zod, and IndexedDB, with optional Better Auth accounts backed by SQLite locally and Turso/libSQL for deployment. Phases 1 and 2 and the local Phase 3 account foundation are implemented. An OpenAI bullet assistant and criterion coaching are implemented; a fictional live coaching development run is recorded below, with independent semantic review still open. The private Turso connection and migrations have been verified locally; hosted deployment and LinkedIn imports remain unverified or planned.

## Run

Use Node.js 20.9 or newer and npm.

```sh
npm install
npm run db:setup
npm run dev
```

Open http://localhost:3000 for the public landing page. **Open my CVs** leads to `/builder`, the existing CV library/editor on the same origin and IndexedDB database. Browse `/templates` and `/examples` without opening a personal repository; detail pages provide read-only rendered previews. **Use this design** selects presentation in the builder, and the explicit **Create my resume** action starts with blank personal details. Browsing, selection and reload do not create documents or copy the example's identity/work history. Old drafts remain available through `/builder`; no storage migration or automatic account import occurs.

Public help and current data-handling information are at `/help` and `/privacy`. Existing `/profile`, `/account`, `/grader`, `/upgrade` and `/pricing` routes remain available; editor return links, reviewer transfers and billing return URLs now point to `/builder`. All previous authentication/export rules remain in force. Account settings now include Profile, Plans, Help and Data & privacy navigation; Google sign-in is available only when its provider credentials are configured.

The builder library shows actual saved-CV thumbnails and supports search, recent/title sorting, independent duplication and confirmed revision-checked deletion. Blank or example-design personal starts offer a collapsible guide; it navigates/focuses fields without adding facts. Mobile editing includes Edit, Preview, Review and save feedback. Bundled product typography, grouped toolbar controls and keyboard/focus improvements are implemented; comprehensive human accessibility review remains open.

## Available

- Contact details plus summary, experience, education, skills, projects, certifications, and languages.
- Editable section headings, visibility and ordering; entry creation, removal and ordering; individually identified bullets.
- Autosave to IndexedDB with visible status and optimistic revision checks across tabs.
- Independent named resume variants and up to 80 undo steps in the current editing session. Switching resumes or reloading clears undo history.
- Twelve editor styles: Classic, Modern, Compact, Creative, Tech Startup, Executive Luxury, Timeline Modern, Minimalist Simple, Consulting, Portfolio, Brand and Research. Open **Design & templates** in the editor toolbar.
- Undo, Design and Export stay in the primary toolbar. **More tools** reveals CV management, writing actions and separate fictional examples. Escape closes the disclosure and returns focus; editor dialogs keep keyboard focus and return it when canceled.
- Seven accent colors, three bundled font families, 10/11/12 pt body text, four density presets, and an optional Creative contact sidebar. Changing the design preserves section order, visibility, and facts.
- Measured, numbered A4/Letter pages shared by preview and browser print; plain-text download and version 1 JSON backup. Long text splits across pages without shrinking the font.
- Validated backup preview; restore to a new resume or replace active content with undo. Unsupported fields/versions are rejected rather than silently dropped.

**My CVs** lists the selected account's documents; **On this device** lists drafts in this browser profile, which may be shared by people using the same browser. Signed-in startup opens the account library unless this tab explicitly chose device storage. **Practice copies** and **Review older drafts** are separate collections. Legacy records without provenance are kept for review rather than classified by a person's name. Signing in never uploads local resumes: use **Account → Review local resumes for import**, select the resumes, and explicitly copy them. Local originals remain independent. Clearing site data, private browsing, or changing devices can lose access; keep authenticated JSON backups.

All app-provided downloads and exports require a current server-verified session. CV/cover-letter exports, recovery backups, clipboard export and app print also require a verified email. Account-data downloads remain accessible to authenticated owners before email verification and without payment. Account documents are loaded by owned ID with revision checks. Exporting a device draft sends a validated snapshot to the application server only after confirmation; exporting does not save it to the account. Sign-in and verification can resume the selected format without discarding edits. PDF failure displays an error and never bypasses authorization through browser print. Billing simulation URLs cannot activate subscriptions. Verification/recovery are implemented and tested locally; live delivery still requires configuration and staging validation.

Resume text is sent to OpenAI only after explicit consent in the account-only AI bullet assistant. PDF is rendered by server Chromium with remote requests and JavaScript disabled. Print at 100% scale with browser headers/footers disabled and the selected paper size. Fonts, browsers and printer settings can affect output. No universal ATS compatibility or exact preview/export parity is claimed. Browser-native copy, screenshots and OS print cannot be prevented by an application.

**Check my CV** and the public `/grader` lead with a deterministic 0–100 content-quality score (`src/lib/linter/resume-score.ts`). Every point comes from a named check, the three highest-value fixes are listed first, and seven benchmark ranges show how the CV compares with common recruiter guidance. Adding a job posting produces a gap analysis: missing keywords, skills listed but never shown in a bullet, experience years and degree mentions. The score describes written content only and is not an ATS or hiring prediction.

**Review writing** shows deterministic findings and observed counts, with no universal ATS score or inferred seniority. Confirm a curated role checklist before viewing term and numeric-pattern observations; unsupported roles receive a general review. Suggested terms cannot automatically add skills. The document text view serializes visible model content. **File diagnostics** checks actual PDF/DOCX/UTF-8 TXT bytes and, with explicit consent, compares their extracted text with the current CV snapshot. Reports show parser/rules versions, file/source hashes, missing or reordered blocks, PDF pages without text, character signals and link targets. Raw extracted text stays available for review; fonts, clipping, visual reading order and ATS acceptance remain **Not checked**. Reports are request-only and stay in the open view; changing the CV marks its comparison stale. The public `/grader` reviewer displays keyword/token overlaps without treating partial matches as verified qualifications. Pasted text is processed in the browser; PDF/DOCX/TXT uploads are sent to the app server, never automatically saved or sent to AI. Uploads are limited to 5 MB, PDFs to 40 pages and extracted text to 200,000 characters; no OCR or password-protected PDF support. DOCX checks its body XML, without analyzing headers/footers or determining physical pages. Review the original file and import notes before saving a device copy. Evaluated role rubrics, saved actual-file diagnostic history and the rest of Q4 remain planned; explicit account job-review history is available as described below. See [Q4 file diagnostics review](docs/plans/q4-file-diagnostics-review.md).

Existing Phase 1 resumes and version 1 backups receive default design settings when loaded. Their facts, IDs, revisions, and section preferences are preserved; no destructive data migration is needed. Unknown settings are rejected. Resume font options use bundled Source Sans 3, Source Serif 4 and Lato, embedded into standalone HTML/server PDF; Word names these fonts and may substitute them on the recipient's device. New blank resumes use 11 pt and photos off. Saved presentation keys remain valid, although typography/wrapping can change. Product controls and display headings bundle Source Sans 3 and Source Serif 4 through `next/font/local`, with no font-service request at build or runtime. See [font sources and licenses](src/app/fonts/README.md).

## Accounts and database deployment

`npm run db:setup` creates `data/cv-builder.db`, applies checked migrations, and generates a private authentication secret in ignored `.env.local` for default local development. It is safe to rerun; an edited applied migration is rejected. Use a new migration for schema changes. Keep database files and secrets out of source control. Restart the dev server after changing environment values.

Open **Account** to create an account, sign in, choose storage, copy selected local resumes, change your password, download account data, or delete the account. Passwords require 12 characters. Authenticated routes derive ownership from the verified session and check the active workspace identity. Revision checks reject concurrent saves/deletes. Imports run in a transaction and remember source IDs per account, so retries cannot duplicate copies. Import receipts survive deletion of an imported resume; duplicate the local original to deliberately import again.

Optional Google setup: configure server-only `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`, register the exact `${APP_ORIGIN}/api/auth/callback/google` redirect URI in Google Cloud, and restart the app. The provider requests OpenID/basic identity scopes. Missing either credential keeps Google unavailable; secrets are not exposed in the account response. See [Better Auth Google setup](https://better-auth.com/docs/authentication/google).

**Continue with Google** opens a separate sign-in window, leaving the editor, undo history and pending export in their original tab. Allow popups for this origin if needed. A device CV open during sign-in retains the device workspace choice on reload; signing in never uploads it. If browser isolation prevents automatic continuation, return to Account settings and use **Continue export**. Existing email accounts must sign in first, verify their email and choose **Link Google** within ten minutes of signing in, using the same Google email; matching emails are not automatically merged. Google-only accounts can use **Set a password by email** through the existing recovery flow. Password reset revokes all sessions and keeps Google linked. A Google-only account can be deleted after a Google sign-in from the last ten minutes and the exact confirmation phrase; accounts with passwords still require their password. Existing account drafts pause if the Google identity changes.

Turso hosts the database; the Next.js application still needs an application host. For a Node-compatible deployment (including Vercel), set these **server-only** environment variables:

- `TURSO_DATABASE_URL`: the remote `libsql://` database URL.
- `TURSO_AUTH_TOKEN`: the database token, stored in the host's secret settings.
- `BETTER_AUTH_SECRET`: a generated secret of at least 32 characters, stable across application instances.
- `APP_ORIGIN`: the exact HTTPS application origin, without a trailing slash.

Run `npm run db:setup` once against the configured deployment database before starting the app; run `npm run build` and deploy with the standard Next.js build/start configuration. The same libSQL client and migrations serve SQLite and Turso. Production account requests reject a local file database rather than storing data on an ephemeral host filesystem. On 2026-10-11 the private Turso connection succeeded and migrations 001–005 were applied to its initially empty database. Restart the app after changing these settings. Local SQLite accounts/CVs are not automatically copied to Turso; browser device drafts remain in their browser storage. Hosted deployment and backup restoration remain unverified.

Account deletion requires the exact confirmation phrase and the current password, or a recent Google-only session as described above. It cascades through account resumes, import receipts, sessions, and authentication records. Browser copies remain; database/provider backups follow the operator's retention policy. Account export includes profile metadata, resumes, and import receipts, excluding password hashes and session tokens. Its bundle is an archive; individual resumes can be restored through the existing JSON import.

Configure server-only `RESEND_API_KEY` and `AUTH_EMAIL_FROM` with a verified sender, plus the exact HTTPS `APP_ORIGIN`, then restart the app. Signup sends a verification link valid for 24 hours; existing unverified accounts can request another link from Account settings. **Forgot password?** requests a generic recovery response regardless of whether an account exists. Recovery links expire after 30 minutes and can be used once; completing a reset revokes every account session. Password change requires the current password and revokes other sessions. Delivery failures for background recovery mail log an event name without recipients, tokens, or message content. Live delivery, spam-folder behavior and the host's background-request support remain staging gates. References: [Better Auth email/password](https://better-auth.com/docs/authentication/email-password), [Resend email API](https://resend.com/docs/api-reference/emails/send-email).

Without an email provider, editing/sign-in remain available but unverified CV exports stay blocked with an explicit setup message. For local development only, `AUTH_EMAIL_MODE=file` writes sensitive links into ignored `data/auth-email-outbox/`; it never delivers mail and is disabled in production. Never publish or share this directory. Browser tests use this mode with a separate `data/e2e.db`, port 3100, and `.next-e2e` build directory; they do not use the normal app database or email provider. Set `E2E_ORIGIN` to another localhost origin with an explicit free port if needed.

Account changes are checked on tab notifications, focus, visibility and every 30 seconds. If a cloud session expires or another account signs in, the existing workspace pauses while keeping the current draft and undo state in that tab. Restore the original session and retry saving, or explicitly **Keep draft on this device** to make an independent local copy before switching. An unsaved account draft is retained in memory until recovery: keep the tab open. Signing out does not silently replace an open account CV. Email links use separate completion pages so the editor tab can stay open.

Current deployment limits: outbound email is not configured or live-verified in this workspace. Better Auth's request rate limiter is enabled in memory; configure shared rate-limit storage or a trusted hosting gateway before a public multi-instance release. Configure trusted proxy/IP handling for the chosen application host. Backup restoration, remote Turso behavior under production load, provider retention, and hosted deployment operations still require live verification. AI evidence is sent only after explicit consent. Resume text is excluded from routine application logging.

## Review a target job

Open **More tools → Tailor for job**, enter the target role/seniority/language and confirm them before analyzing the pasted posting. The browser-local review shows exact job quotes, editable required/preferred priorities and cited excerpts from visible CV sections. Direct text support, partial/related mentions, not-found evidence and manual review stay separate. Unknown items are outside the scorable denominator; no ATS percentage or hiring probability is displayed. The explicit English term dictionary cannot interpret arbitrary job semantics; years, ambiguous credentials, unfamiliar terms and other languages require manual review.

Review each proposed bullet order and explicitly accept it, then confirm the cited evidence before **Create reviewed variant**. Up to three proposals reorder existing bullets without adding, rewriting or removing facts. The independent variant preserves the source CV, its provenance and presentation. A current/saved source revision change blocks saving, duplicate clicks cannot create two copies, and unconfirmed saves keep the open review and the same pending variant ID for retry. If an account save committed but its response was lost, retry confirms that exact untouched variant without creating another copy. **Undo reviewed variant creation** removes the untouched variant and opens the original; later variant edits prevent its deletion. This undo receipt lasts for the open editor session.

Device reviews stay in the open view. For an account CV, explicitly confirm retention and choose **Save job review** to keep the posting, reviewed priorities and cited excerpts. The server recomputes the review from the owned saved CV; it does not accept browser-submitted evidence scores or call an AI provider. Reports preserve rule/term versions, analysis/save times, job/source SHA-256 and the CV revision, without storing a full CV snapshot or photo. Save and delete retries recover lost responses without duplicating history. Run `npm run db:setup` to apply the additive history migration before starting an existing installation.

**Saved job reviews** survives reload. Historical reports are read-only and marked stale when the CV snapshot or review rules change. **Recheck this posting** restores its input for a new review against the current CV and requires target confirmation again. Delete individual reports here; deleting their CV or account also removes them. Account-data export includes saved reports. Signing in alone does not upload a device review. Limits are 20 reports per CV, 100 per account and 512 KB per report; full history rejects new saves without removing older records.

Review input limits remain 20,000 posting characters, 60 criteria, 1,000 visible CV excerpts, 200,000 visible CV characters and three displayed excerpts per criterion. Actual-file diagnostics remain request-only. Shared Master Vault projections, evaluated semantic AI coaching and the held-out benchmark remain planned. See [Q4 job-evidence review](docs/plans/q4-job-evidence-review.md) and [Q4 saved-history review](docs/plans/q4-job-review-history.md).

**Coach criterion** uses the configured OpenAI connection for an account CV after explicit in-app consent. The app server validates the full posting against the owned saved CV, then sends only one selected criterion, target role/seniority/language/company, the selected entry's bullets and your writing instruction to OpenAI. Contact fields, other entries and the full posting are excluded. A separate call audits the assessment, message and questions; a candidate-only check audits any proposed rewrite. Failed checks withhold the suggestion. Citation validation, factual confirmation, acceptance/rejection, revision guards and session Undo remain required. This slice supports English and withholds duration interpretations. Local coverage counts stay unchanged.

Coaching shares the bullet assistant's account request ledger, daily/concurrency limits and immutable retries. Up to three structured calls use one 45-second deadline, 1,800 output tokens each, `store: false` and no automatic paid retries. A coaching attempt counts as one application request even when it uses multiple provider calls; failed attempts count. No provider key means unavailable coaching without charging usage. Proposals include criterion/context metadata, original entry references and prompt/model versions in account storage/export; rejection or CV/account deletion removes proposal content. Provider retention remains deployment-dependent. Integration tests use controlled synthetic replies and do not establish semantic model quality or complete the 120-pair held-out gate. See [Q4 coaching integration review](docs/plans/q4-job-coaching-review.md).

## OpenAI bullet assistant

Use **Writing help** or a bullet’s **Improve this bullet → Rewrite with AI** action to open the **AI bullet assistant**. The selected source stays visible, suggestions are reviewed before acceptance, and the dialog can be closed while generation is pending. It requires an account workspace, a nonempty bullet, and explicit consent to send the selected entry's bullets and writing instruction. It does not upload local resumes or send contact fields or other entries. Instructions express writing preferences; add new candidate facts to the original entry before asking for another rewrite.

Add `OPENAI_API_KEY` privately to `.env.local` (or the deployment's secret settings), then restart the app. Do not put keys in chat or any `NEXT_PUBLIC_` variable. `OPENAI_MODEL` defaults to `gpt-4.1-mini-2025-04-14`; model access and actual output quality still require testing with your OpenAI project. Run `npm run db:setup` for the proposal/usage migration.

An inherited `OPENAI_API_KEY` takes precedence over `.env.local`. If a newly saved file key still returns authentication errors, clear the stale variable in the launching PowerShell process with `Remove-Item -LiteralPath Env:OPENAI_API_KEY -ErrorAction SilentlyContinue`, then run the command or restart the app from that process. This does not edit the key file or permanent environment settings. Never print the key to diagnose precedence.

The server calls the Responses API with strict JSON output and `store: false`. A second structured call checks factual support. Invalid references, new numeric claims, incomplete output, refusals, and failed support checks cannot become applicable edits. The model has no tools, URLs to fetch, or mutation privileges. Semantic checks can still make mistakes: the user reviews the original evidence and proposed wording, confirms factual accuracy, and chooses **Accept and save** or **Reject suggestion**. Acceptance derives content from the server-stored proposal, checks ownership and revision, and saves the resume and acceptance receipt in one transaction. Repeated acceptance cannot apply twice; session Undo can restore the original text.

Limits: at most 10 evidence bullets/12,000 characters per entry, a 1,000-character instruction, two provider calls with 1,800 output tokens each, and a 45-second total timeout with no automatic paid retries. Database-backed counters default to 20 rewrite requests per account/day and 200 installation-wide/day (UTC), configurable through `AI_DAILY_USER_LIMIT` and `AI_DAILY_GLOBAL_LIMIT` (0 disables new generation). Failed attempts count; deleting resumes cannot reset these counters. At most two requests per account may be active within the 90-second reservation window. Provider/project spending limits should also be set for the chosen deployment.

Proposals expire for acceptance after 24 hours. Pending/accepted proposal content, original evidence snapshots, and prompt/model versions remain in account storage until the resume/account is deleted; rejection clears the proposal body. Usage counters and receipt metadata remain with the account and are included in account export. Account deletion removes account-specific AI records; anonymous installation-wide daily totals remain. `store: false` is not a promise of zero provider retention; verify the OpenAI project's data settings before release.

Controlled provider responses and real SQLite validate consent, evidence checks, accept/reject/undo, stale writes, ownership, retry receipts, quotas, malformed output, refusal, timeout and mobile layout. The updated private key succeeded after clearing a stale inherited key for the evaluation process. The twelve-case fictional coaching run with configured/returned `gpt-6-luna` completed with 11 development checks passing and one SQL assessment withheld by the support audit. Independent semantic review remains open. `npm run ai:eval` separately runs four synthetic general-bullet smoke fixtures (up to eight paid API calls) without touching saved resumes; that live command has not been verified in this coaching run.

For criterion coaching, use `npm run ai:eval:job -- --dry-run --limit=24` to validate the 24 agent-authored fictional development cases with zero provider calls. `npm run ai:eval:job -- --live --limit=12` explicitly makes paid calls using the production coaching adapter: at most 36 requests, sequential cases, no automatic retries, and early stop on authentication/quota/connection failure. JSON reports are atomically saved after each case in ignored `test-results/job-coaching-evaluations/`. They preserve raw versus final judgments, audits, versions/hashes, reported tokens, elapsed time and role-group denominators. Provider error bodies/credentials and saved CVs are excluded. Limit may be 1..24; the default is 12. The reports always leave independent semantic review and the held-out release gate open. See [Q4 evaluation findings and independent review protocol](docs/plans/q4-ai-evaluation-review.md).
